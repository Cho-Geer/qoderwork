# Blueprint 创建流程

## Language / 语言

Follow the user's language: reply in Chinese for Chinese requests and English for English requests. Provide both only when requested; preserve code, commands, paths, API names, identifiers, and quoted source text exactly.

创建框架级变更 blueprint 的标准化流程。Blueprint 是经过多轮迭代收敛后的完整实施方案文档，用于指导框架级改动的实施。

## 前置条件

开始创建 blueprint 前，必须具备以下信息：

1. **明确的问题描述**：知道要解决什么问题，不是模糊的"优化"或"改进"
2. **根因已验证**：通过实测（日志分析、ACP session 测试、代码审查）确认了因果链，而非基于推测
3. **现有机制已调查**：了解框架中是否已有类似功能可以复用或扩展
4. **约束条件已明确**：知道运行时约束（如上下文窗口大小、性能开销）和架构约束（如必须兼容现有 checklist 系统）

## 核心原则

### 实测优先于推测

根因分析必须基于实测验证。通过日志分析、ACP session 测试、代码审查等手段确认因果链后，才能进入方案设计。

> **步骤类型区分**：「日志分析」和「serve API / session 测试」是 `[VERIFICATION]`（产出运行态证据）；「代码审查」是 `[ANALYSIS]`（仅产生理解）。根因结论必须基于至少一项 `[VERIFICATION]` 证据，不能仅凭代码审查。
> **Verified-by 要求**：每次 `[VERIFICATION]` 后都要记录 `Verified-by: <命令/接口> -> <关键返回/日志/产物路径>`。
> **合理化检测**：如果你发现自己在想「代码看起来就是这样，所以根因已经确定了」--停下来，这是跳步信号。必须补足运行态验证。
> **认知说明**：代码审查回答“实现意图是什么”；运行态验证回答“实际发生了什么”。两者不一致时，以证据为准。

**反面案例**：假设"agent 不读取 skill 是因为 skill 内容没有注入 system prompt"，但实测发现 agent 确实没有调用 `read_skill()`，根因是"没有硬约束强制 agent 读取"而非"注入缺失"。

### 复用优先于新建

优先扩展现有机制，而非创建新的 hook、tool 或 system。

**实际案例**：框架已有 `config_read_attest` 工具（通过 `read_audit` 表验证 agent 是否读取了配置文件）。扩展这个模式创建 `skill_read_attest` 和 `rule_read_attest`，比新建一个 before-hook 更一致、更易维护。

### 迭代收敛

方案选择应记录否决方案的理由。用户在多轮修正中达到的稳定输出规格（如 3文件→1文件、before-hook→attest模式、TTL→hash比对）本身就是宝贵的设计决策。

### 上下文意识

方案设计需考虑运行时资源约束。例如：要求 agent 读取 `opencode.json`（~80KB）和 `project.config.json`（~20KB）会占用大量上下文窗口，如果 Agent .md 是自包含的，可以只要求读取 1 个文件，节省 ~100KB。

### 可回滚性

每个方案必须包含明确的回滚路径。如果实施后出现问题，能够快速恢复到之前状态。

## 标准操作流程（6 阶段）

### Phase 0: 问题定义与根因分析

**目标**：明确问题是什么、为什么发生、通过实测确认因果链。

**输出内容**：

1. **问题描述**：一段话说明问题现象和影响
2. **直接原因**：导致问题的直接技术原因
3. **根本原因**：为什么直接原因会发生（架构/设计层面的缺陷）
4. **实测验证**：通过什么手段验证了因果链（ACP session 测试、日志分析、代码审查等）
5. **结论**：一句话总结根因

**格式示例**：
```markdown
## 一、问题背景

### 1.1 问题描述
[问题现象和影响]

### 1.2 根因分析
**直接原因**：[技术层面的直接原因]
**根本原因**：[架构/设计层面的缺陷]

### 1.3 实测验证
[通过什么手段验证了因果链]
**结论**：[一句话总结]
```

### Phase 1: 方案设计（多选项对比）

**目标**：提出至少 2 个方案，明确优劣对比和选择理由。

**输出内容**：

1. **方案列表**：每个方案包含核心思路、优势、劣势
2. **对比表**：按关键维度（如实现复杂度、可维护性、性能、兼容性）对比
3. **选择结论**：选定哪个方案，为什么
4. **否决理由**：其他方案为什么被否决

**格式示例**：
```markdown
## 二、解决方案

### 2.1 方案对比

| 维度 | 方案A | 方案B | 方案C |
|------|-------|-------|-------|
| 核心思路 | ... | ... | ... |
| 实现复杂度 | ... | ... | ... |
| 可维护性 | ... | ... | ... |
| 性能开销 | ... | ... | ... |

### 2.2 选择结论
选择方案 [X]，理由：[为什么]

### 2.3 否决理由
- 方案 [Y]：[否决原因]
- 方案 [Z]：[否决原因]
```

### Phase 2: 核心设计详述

**目标**：选定方案的详细设计，包含数据模型、代码变更示意、配置变更、与现有机制的关系。

**输出内容**：

1. **方案概述表**：需求 → 解决方案的映射表
2. **数据模型变更**：数据库 schema 变更、新增字段、接口定义
3. **代码变更示意**：关键代码片段（TypeScript），展示核心逻辑
4. **配置变更**：配置文件的增删改
5. **与现有机制的关系**：明确说明是复用、扩展还是新建
6. **子系统合规检查清单**：逐项审计方案对框架 12 个子系统的合规性（见下方清单）

**格式示例**：
```markdown
### 2.2 核心设计

#### 2.2.1 [组件名称]
[代码示意和设计说明]

#### 2.2.2 [组件名称]
[代码示意和设计说明]

#### 2.2.N 子系统合规审计

逐项检查方案对以下 12 个框架子系统的影响与合规性。每项标注 ✅ 合规 / ⚠️ 需注意 / ❌ 不合规，不合规项必须在设计阶段修复。

| # | 子系统 | 状态 | 检查要点 |
|---|--------|------|----------|
| 1 | MVC Architecture | ✅/⚠️/❌ | 数据访问/业务逻辑/路由分层是否清晰 |
| 2 | DB-only & DB-canonical | ✅/⚠️/❌ | 是否存在文件队列等 DB 冗余数据源 |
| 3 | Permission Matrix | ✅/⚠️/❌ | agent 工具权限矩阵是否需要同步更新 |
| 4 | Concurrency Safe | ✅/⚠️/❌ | 事务隔离级别（IMMEDIATE vs DEFERRED）、UPDATE 守卫条件、TOCTOU 防护 |
| 5 | Hardened Enforcement | ✅/⚠️/❌ | 硬约束 plugin hook 是否覆盖新增路径 |
| 6 | Framework Harness | ✅/⚠️/❌ | 框架 harness 兼容性 |
| 7 | Central State Management | ✅/⚠️/❌ | 状态是否收敛到中央管理（避免分布式状态） |
| 8 | Multi-Agent | ✅/⚠️/❌ | 多 agent 调度/隔离是否受影响 |
| 9 | Log Central Management | ✅/⚠️/❌ | 日志通道是否统一（所有 hook 统一走 writeLog → .task_temp/_logs/） |
| 10 | DB-canonical Management | ✅/⚠️/❌ | DB schema 变更是否符合规范（零迁移优先） |
| 11 | Templatization & Parameterization | ✅/⚠️/❌ | 配置是否参数化、避免硬编码 |
| 12 | TypeScript + Bun Runtime | ✅/⚠️/❌ | 文件行数（≤400行目标）、外部依赖（禁止 npm）、bun 兼容性 |

**实际案例**：某 dispatch 系统 blueprint 在完成后审计发现三个缺陷——`dbDequeueWithLease()` 的 UPDATE 缺少 `AND status = 'pending'` 守卫导致 TOCTOU 并发漏洞（子系统 4）；`consumeDispatchMarker()` 在 before-hook 路径上使用 `process.stderr.write` 违反日志集中管理（子系统 9）；新增代码导致 router.ts 超过 400 行目标（子系统 12）。这些缺陷在设计阶段通过合规审计即可发现。
```

### Phase 3: 实施清单

**目标**：列出所有需要变更的文件，以及分阶段的实施步骤。

**输出内容**：

1. **文件变更表**：序号、文件路径、变更类型（新建/修改/Schema）、说明
2. **实施步骤**：分阶段列出，每阶段含工时估算和依赖关系

**格式示例**：
```markdown
## 三、实施清单

### 3.1 文件变更列表

| 序号 | 文件 | 变更类型 | 说明 |
|------|------|---------|------|
| 1 | path/to/file.ts | 修改 | [说明] |
| 2 | path/to/new.ts | 新建 | [说明] |

### 3.2 实施步骤

**Phase 1: [阶段名称]（X天）**
1. [步骤]
2. [步骤]

**Phase 2: [阶段名称]（X天）**
3. [步骤]
4. [步骤]
```

### Phase 4: 验证计划

**目标**：三层验证确保实施正确性。

**输出内容**：

1. **单元测试**：针对单个函数/模块的验证项
2. **集成测试**：针对模块间交互的验证项
3. **端到端测试**：针对完整流程的验证项
4. **子系统合规验证**：针对 Phase 2 合规审计中标注 ⚠️ 或 ❌ 的子系统的专项验证项

所有验证项使用 checkbox 格式（`- [ ]`），方便实施时勾选。

**格式示例**：
```markdown
## 四、验证计划

### 4.1 单元测试
- [ ] [验证项描述]
- [ ] [验证项描述]

### 4.2 集成测试
- [ ] [验证项描述]
- [ ] [验证项描述]

### 4.3 端到端测试
- [ ] [验证项描述]
- [ ] [验证项描述]

### 4.4 子系统合规验证
针对 Phase 2 合规审计结果，对受影响子系统逐项验证：
- [ ] [子系统名称]：[具体验证项，如：并发 dequeue 竞争测试——两个事务同时 dequeue 同一 agentType，仅一个成功]
- [ ] [子系统名称]：[具体验证项，如：日志通道检查——确认所有 hook 统一走 writeLog → _logs/]
- [ ] [子系统名称]：[具体验证项，如：文件行数检查——确认改造后文件不超过 400 行目标]
```

### Phase 5: 风险与回滚

**目标**：识别风险、制定缓解措施、明确回滚路径和成功标准。

**输出内容**：

1. **风险表**：风险、影响、缓解措施
2. **回滚方案**：如果出现问题，如何恢复
3. **成功标准**：用 checkbox 列出可衡量的成功指标

**格式示例**：
```markdown
## 五、风险与缓解

### 5.1 风险

| 风险 | 影响 | 缓解措施 |
|------|------|---------|
| [风险描述] | [影响] | [措施] |

### 5.2 回滚方案
[具体的回滚步骤]

## 六、成功标准
- [ ] [可衡量的指标]
- [ ] [可衡量的指标]
```

## 陷阱与注意事项

1. **不要在根因未验证时就进入方案设计**。实测验证是 Phase 0 的硬性要求。跳过实测会导致方案建立在错误假设上。

2. **不要忽视现有机制**。框架中往往已有类似功能（如 config_read_attest、read_audit、checklist 系统）。先调查、再设计，避免重复造轮子。

3. **不要只提一个方案**。至少提出 2 个方案进行对比，记录否决理由。单方案容易陷入"唯一解"的思维陷阱。

4. **不要忘记上下文窗口约束**。要求 agent 读取大文件（如 80KB 的配置文件）会严重影响性能。方案设计时需评估 token 开销。

5. **不要省略回滚方案**。每个变更都必须有回滚路径。如果无法回滚，需要在风险表中明确说明并给出替代方案。

6. **文件变更表必须完整**。实施清单中的文件列表应覆盖所有需要变更的文件，包括数据库 schema、配置文件、新建文件。遗漏文件会导致实施时返工。

7. **验证计划必须分层**。单元测试、集成测试、端到端测试三个层次缺一不可。只有单元测试不足以验证系统集成正确性。

8. **Blueprint 保存位置**：保存到项目的 `blueprints/` 目录下，文件名格式为 `blueprint-[简短描述].md`。

9. **不要在 blueprint 完成后跳过子系统合规审计**。Phase 2 的 12 子系统合规检查清单是设计阶段的必要环节，不是可选的附加步骤。实际案例：某 dispatch 系统 blueprint 跳过了合规审计，实施后才发现三个缺陷——TOCTOU 并发漏洞（UPDATE 缺少 `AND status = 'pending'` 守卫）、before-hook 日志通道违规（在统一 writeLog 的框架中混用 `process.stderr.write`）、文件行数超标（router.ts 超过 400 行目标）。这些缺陷在设计阶段通过合规审计即可发现，实施后修复的成本远高于设计阶段调整。
