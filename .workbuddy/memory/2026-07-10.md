# MCP tool 透传 call_id 机制 (源码确认, 2026-07-10)

**权威来源**: @opencode-ai/plugin v1.17.18 类型定义 (jsdelivr CDN) + 官方 plugins/MCP 文档。
**确认事实**:
- tool.execute.before input 含 callID:string (typed, 必存在) + sessionID + tool。
- tool.execute.before output 为 { args:any } 且可变——官方示例对 bash 做 output.args.command=escape(...)，证明 output.args 即工具实际收到的参数。
- MCP 工具按官方文档是 "available as tools... alongside built-in tools"，hooks 同样触发，before-hook 对 MCP 工具生效。
- 项目 gate-call-context.ts:60 只写 input._gateCallContextId (仅 after-hook 可见)，没写 output.args → MCP handler 收不到 call_id，这正是 mcp-confirm 用 created_at DESC LIMIT 1 fallback 的根因之一。

**Fix A 确定形态 (修正上轮 map/自定义 tool 猜测)**: before-hook 注入 output.args.call_id = input.callID (+ output.args._gateCallContextId)，MCP 工具 zod inputSchema 加 call_id: z.string().optional() 防被 schema 剥离。无需进程内 map、无需迁移到 plugin custom tool。
**Fix B**: resolveGateCallContextStrict 强制 call_id 精确匹配、删 ORDER BY created_at DESC LIMIT 1、非恰好1行返回 null(fail closed)；删 resolveGateCallContextBySession 松兜底。
**残留风险**: 需 E2E 确认 OpenCode 把 output.args(含注入字段) 原样派发到 MCP server。

- GATE SCHEMA (declared_deliverables) 由武装 gate 的一方 (本例 build 子 agent 自己调 compliance_gate_check 合并流, 见 prompt-sections.ts:134-158) 手工填结构化数组, 非豁免仅自动追加 HANDOVER.md/TASK_LOG.md (mcp-confirm.ts:258/343)。
- 两份 spec 是 两个独立生成产物 (不同入口/不同 agent/不同数据形态), 无任何代码桥接 (grep service/dispatch/ 无 declared_deliverables 引用)。
- 第三处解耦: 目录名也独立 - plan 用 session_namespace (orchestrator-test-write), gate 用 cg_ses_<id>/ (mcp-confirm.ts:264)。
- 历史尝试 prompt-builder.ts.bak-pre-t17:163 曾注入 dag_task_id 但已成 .bak 死代码, 且只桥 task_id 未桥 deliverables。
- 结论: 一致性全靠 LLM 自觉, 系统用报错驱动对齐 (build 4 次失败才学会 schema)。根治三层级: (最小) prompt-sections.ts gate flow 段强约束 plan 产物必须同时 declared; (中) dispatch 自动预填 declared_deliverables; (彻底) 统一 session_namespace 与 gate task_id/artifact 目录。

**真正的 taskId (dag_task_id) 生成点 — 源码证据 (2026-07-10)**:
- 入口工具 `dispatch_subagent.ts:20/49` 接收可选 `dag_task_id` / `session_namespace` / `auto_plan` 入参, 透传给 `router.dispatch()` (router.ts:128/152)。
- **生成/解析优先级 (router.ts:207-209)**: `effectiveDagTaskId = dagTaskId || sessionNamespace || ""`; 若三者皆空 → `require("node:crypto").randomUUID()` 兜底自动生成 (事件 DAGTASK-ID-AUTO-GENERATED)。
- **常态来源**: Orchestrator 从 `Task.DAG.json` 规划好的条目取 `dag_task_id` 传入; 或 `auto_plan=true` 时 `autoPlan()` (service/dispatch/dag-policy.ts:182) 用 `dispatchMetaPlanner` 跑 `dispatch-subagent.ts Meta-Planner <dagTaskId>` 把该 id 写进 Task.DAG.json (autoPlan 不自己生成 id, 用传入的 opts.dagTaskId)。
- **落库 (canonicalDagId = dagTaskId || effectiveDagTaskId)**: router.ts:366 写 session_map; router.ts:394-396 写 session_events; queue.ts:70-72 写 dispatch_queue。
- **第四处解耦 (关键!)**: validateDispatchTaskIntegrity("") 的 else 分支 (dispatch-integrity.ts:101-130) 本应从 `.task_temp/_dispatch/ctx/{dagTaskId}.json` 回退解析真实 taskId (行159 `resolvedTaskId=dispatchAssignedTaskIds[0]`); 但写该 ctx 文件的 `writeDispatchCtx()` (service/session/dispatch-context.ts:19) **在现行代码里无任何调用方 (死代码)** → ctx/ 不被写出 → 回退拿不到 → gate check 时 effectiveTaskId=null (mcp-check.ts:194) → 本例 gate task_id=null → submit 退回 cg_ses_xxx。这把"plan 与 gate 目录对不上"的根因补实: 真实 taskId (orchestrator-test-write) 只进了 session_map/session_events, 没进 gate。

**task id (dag_task_id) 数据规则调查 — 源码证据 (2026-07-10)**:
- **DB 层无 UNIQUE 约束**: `dag_task_id` 在 session_log (db-manager.ts:472) / dispatch_queue (1154) / dispatch_context (1216) 均为 `TEXT NOT NULL`, session_map 经 ALTER 加为 `TEXT DEFAULT NULL` (593)。无一处 UNIQUE。唯一 UNIQUE 索引在 dispatch_queue.dispatch_key (1174), 但 `dispatch_key = crypto.randomUUID()` (queue.ts:63 / router.ts:197), **与 task id 无关 → 复用同名 task id 不会触发 UNIQUE 冲突**。
- **session_map 主键是 session_id 非 dag_task_id**: 复用 namespace 会在 session_map 产生多行同 dag_task_id (DISTINCT 折叠), 合成 entry `dispatch:child:<ns>` (router.ts:385) 在重派时会 upsert 覆盖 (无报错)。
- **入参零格式校验**: `dispatch_subagent.ts:20` `dag_task_id` 为 `schema.string().optional()`; `:22` `session_namespace` 为 `schema.string()` (required, router.ts:158 空则 throw)。两者均无 regex/长度/字符集规则 → `orchestrator-test-write` 之类自由串 100% 通过。
- **约定 (非强制) 的 task id 形态**: Task.DAG.json 真实 id 为语义化大写连字符 (`E2E-PLUGIN-REGISTER`, `CALLER-ID-PHASE-0`), 且 `outputs` 写成 `.task_temp/<task_id>/HANDOVER.md` → 设计不变量是 `namespace === dag_task_id === output dir` 三者同一令牌。但**无任何代码强制此不变量**。
- **程序化"生成器"只有两个且都不产出 task id 格式**: (1) `crypto.randomUUID()` 仅用于 dispatch_key / 以及 dag+namespace 皆空时的兜底 effectiveDagId (router.ts:209); (2) `Date.now()` 仅用于 gate session id `cg_ses_xxx` (store-crud.ts:335)。**真正的 dag task id 由 @Meta-Planner 写 Task.DAG.json 时 LLM 创作 (generated_by 字段), 无任何 regex 校验器; autoPlan() 不生成 id, 只把传入的 opts.dagTaskId 登记进 DAG**。
- **语义层"期望唯一/注册"但非强制**: validateDispatchTaskIntegrity (dispatch-integrity.ts:136-156) 把 dag_task_id 当"不可变、已注册"令牌, 编造未注册 id → DISPATCH_TASKID_TAMPER; router.ts:226 `findTaskInDag(dagTaskId)` 要求其在 Task.DAG.json 存在 (仅当真传了 dag_task_id 且 PLAN-FIRST 检查跑时)。但这些是条件检查, 不是全局唯一/格式约束。
- **结论/修正**: 我之前说"dispatch_key UNIQUE 会拦重复 task id"是错的——dispatch_key 是 randomUUID, 不派生自 task id, 故不提供该保护。task id 在 schema 层**完全无唯一性/格式约束**, 自由串皆可; 其"唯一/注册/稳定"只是设计意图 (靠 session_map 查询与 DAG outputs 隐式依赖), 非数据规则。这正解释了为何 `orchestrator-test-write` 能被当 task id 用且与 gate 的 cg_ses_xxx 静默分叉。
