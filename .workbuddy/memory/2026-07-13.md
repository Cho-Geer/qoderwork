## work-one before 链验证：tool-governance 对 `safe_shell gh issue create` 的命中顺序

**任务**: 用 /pre-flight-enforcement 确认 `safe_shell gh issue create --repo ...` 在真实 active before 链上先命中 tool-governance（而非仅 unit/component 测试）。

**结论**: ✅ 已确认。真实 `before-dispatcher` 执行序列 = guidance-bridge → permission-safety → behavioral-path-guard → scope → **tool-governance**(HANDLER-BLOCK [REPO-OP]) → 链短路；path-validate/codegraph 未执行。tool-governance 为首个且唯一 denier。

**关键事实/可复用方法**:
- `before` 链是单一 `tool.execute.before` hook（`plugins/before-dispatcher.ts`），内部按 `project.config.json` 的 `plugin_execution_order.before`（与 DEFAULT_ORDER 一致）串行调度，首个 throw 短路。tool-governance 位于 index 6。
- **live 验证真实 dispatcher 的方法**：`bun x esbuild before-dispatcher.ts --bundle --format=esm --platform=node --external:bun:sqlite` 后 `bun run` 打包产物。绕开 `bun run` 直接加载报 `export 'parseShellWriteTargets' not found`（tool-scope-paths ↔ shell-targets 循环 re-export，bun 原生 ESM 链接失败；仅 serve 的打包器能解析）。
- **测试只停留在 unit/component 的根因**：上述循环 re-export 导致 `before-dispatcher` 无法被 `bun run` 独立加载，故现有测试只能直接 `handle()` 单个 handler，无法测排序。
- 日志落点：`writeLog` 写 JSONL 到 `<root>/.task_temp/_logs/<date>/`（非 `.opencode` 内）；HANDLER-START/HANDLER-BLOCK 在 `plugin-before-dispatcher-runtime.log`，deny 汇总在 `audit.jsonl`。
- 安全：tool-governance 在工具执行前拒绝，gh 未实际运行，未创建真实 issue。
