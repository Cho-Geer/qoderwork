你的判断非常准确，这正是 OpenCode 架构设计最核心的「轻量扩展范式」：**原生 Agent 做标准化执行器、Skill 注入领域能力、Hook 做全局治理**，三者正交组合，完全可以覆盖绝大多数复杂项目的开发、构建、部署全流程，甚至比堆砌大量自定义 Agent 的方案更稳定、易维护、可复用。

先做一个概念澄清：你提到的 `plan`、`build` 是**主代理（Primary Agent）**，`explore`、`general` 是**子代理（Subagent）**。OpenCode 官方内置标准化执行单元为 `plan` / `build` / `general` / `explore`（合计 4 个；原 `scout` 子代理在 OpenCode v2 已废弃，外部调研改用 `explore`），覆盖从规划、编码、探索到调研的研发全链路核心角色。

## 一、为什么原生 Agent 足以支撑全流程
OpenCode 内置的 5 类代理，本质是官方经过大量场景调优的「专用执行器」，各自有明确的定位、优化过的系统提示词和匹配的工具集。绝大多数场景下，你不需要重新发明轮子，只需要通过 Skill 给它们注入领域知识，通过 Hook 加上流程护栏。

### 1.1 主代理层：交互入口 + 流程中枢
| 内置代理 | 定位 | 原生能力边界 | Skill 增强方向 | Hook 管控方向 |
|---|---|---|---|---|
| **Plan** | 规划分析主代理 | 默认只读受限，`file edits` / `bash` 权限为 `ask`，只做分析、提方案、拆任务，不落地修改 | 架构设计方法论、项目拆解规范、风险评估清单、技术选型标准 | 方案合规校验、输出格式标准化、自动生成评审单 |
| **Build** | 编码执行主代理 | 默认全工具开放，负责日常开发、文件修改、命令执行 | 编码规范、框架最佳实践、单测编写标准、重构方法论 | 写入前代码格式化、安全扫描、提交信息规范、命令审计 |

### 1.2 子代理层：并行执行 + 专项分工
子代理运行在独立会话中，不占用主会话上下文，适合并行拆解任务，是复杂项目协作的核心单元。

| 内置子代理 | 定位 | 原生能力边界 | Skill 增强方向 | Hook 管控方向 |
|---|---|---|---|---|
| **General** | 通用执行子代理 | 除 `todo` 外全工具权限，负责多步骤专项任务，可修改文件 | 模块开发规范、故障排查手册、部署操作流程 | 高风险操作二次审批、执行结果自动校验、日志归档 |
| **Explore** | 只读代码探索子代理 | 纯只读，快速梳理代码结构、调用关系、存量逻辑 | 架构梳理方法、代码异味检查清单、依赖梳理规范 | 敏感代码脱敏、分析报告自动生成、只读权限强制 |
| **Scout（已废弃）** | 外部调研子代理（v2 已移除） | 原只读调研代理；OpenCode v2 已不内置，外部调研改用 `explore` | — | — |

> 这 5 类代理已经覆盖了软件研发的「规划 → 探索 → 编码 → 调研 → 执行」全环节。官方持续优化它们的提示词、工具调用策略和上下文管理，稳定性远高于手写的自定义 Agent。

## 二、Skill + Hook + 原生 Agent 的三层落地架构
完全不需要自定义 Agent，通过三层架构即可搭建完整的项目研发工作流：

### 第一层：能力层 —— 细粒度 Skill 集合
把所有领域知识、业务规范、流程标准拆成**单一职责的 Skill 单元**，作为可插拔的能力组件，按需分配给不同代理。

典型 Skill 分类：
- **规范类**：编码规范、Git 提交规范、接口文档规范、数据库设计规范
- **技术类**：框架最佳实践、性能优化方法论、单元测试编写指南
- **流程类**：发布操作手册、故障排查 SOP、回滚预案、线上变更流程
- **合规类**：安全检查清单、开源许可证合规、数据脱敏规则、权限申请流程

核心原则：Skill 只定义「怎么做才对」，不绑定特定 Agent，同一个 Skill 可以同时授权给 General 子代理和 Build 主代理。

### 第二层：管控层 —— Plugin Hook 横切治理
所有通用的、跨 Agent 的治理逻辑全部通过 Hook 实现，不散落进各个 Skill 里，做到一处修改、全链路生效。

核心配合点：
1. **配置注入（`config` Hook）**
   - 按环境动态加载不同 Skill 集：开发环境加载调试类 Skill，生产环境只加载运维、部署类 Skill
   - 动态注入团队统一的权限规则，替代每个项目单独配置

2. **加载拦截（`tool.execute.before` Hook）**
   - Skill 白名单管控：不同 Agent 只能加载授权范围内的 Skill，比如 Explore 绝不允许加载部署类 Skill
   - 版本路由：根据项目类型自动切换对应版本的 Skill 内容
   - 调用审计：记录谁、何时、加载了哪个 Skill，形成全链路追溯

3. **内容增强（`tool.execute.after` Hook）**
   - 自动追加企业合规说明、内部链接、安全提示到所有 Skill 末尾
   - 对敏感 Skill 内容做脱敏处理
   - 统一 Skill 输出格式，确保所有代理遵循相同的指令风格

4. **权限治理（`permission.*` Hook）**
   - 低风险 Skill 自动审批放行，减少用户打断
   - 高风险 Skill（如生产部署、数据库变更）强制二次校验
   - 按时间段、用户角色动态调整权限策略

5. **生命周期管理（`session.*` Hook）**
   - 子代理会话创建时自动注入对应角色的 Skill 权限集
   - 会话销毁时自动归档 Skill 使用记录与执行结果
   - 上下文压缩时优先保留核心 Skill 内容

### 第三层：执行层 —— 原生 Agent 标准化执行
所有具体任务都交给原生 Agent 执行，不修改其基础人设与提示词，只通过权限和 Skill 集做差异化配置。

典型协作模式：
```
用户提需求
   ↓
Plan 主代理 + 项目规划 Skill → 输出任务拆解方案
   ↓
Explore 子代理 + 架构梳理 Skill → 输出存量代码分析报告
   ↓
General 子代理 + 编码规范 + 单测 Skill → 并行开发多个模块
   ↓
Build 主代理 + 发布流程 Skill → 执行构建与部署
   ↓
Explore 子代理 + 依赖合规 Skill → 事后做依赖审计
```

全程没有任何自定义 Agent，全部由原生执行器 + 可插拔能力 + 全局管控组成。

## 三、相比「大量自定义 Agent」的核心优势

### 1. 稳定性与可靠性更高
原生 Agent 的系统提示词、工具调用逻辑、错误处理机制经过官方持续迭代优化，极少出现指令冲突、工具滥用、逻辑跑偏等问题。自定义 Agent 往往因为提示词写得不完善，出现人设漂移、权限越界等问题。

### 2. 可组合性极强
Skill 是正交的能力单元，可以任意搭配给不同 Agent；自定义 Agent 往往是高度耦合的，加一项能力就要修改整套提示词，很容易牵一发而动全身。

### 3. 维护成本极低
- Skill 是 Markdown 文档，开发、测试、运维、产品都可以参与贡献
- Hook 是集中式横切逻辑，改一次全链路所有 Agent 都生效
- 不需要维护一堆自定义 Agent 文件，也不需要处理它们之间的兼容问题

### 4. 上下文效率更优
Skill 是按需加载的，不用就不占用上下文窗口；自定义 Agent 的长提示词是常驻的，Agent 越多、提示词越长，上下文浪费越严重，有效工作空间越小。

### 5. 可移植性更好
Skill 和 Hook 可以跨项目、跨团队直接复用；自定义 Agent 往往和具体项目的业务逻辑深度绑定，很难直接迁移。

## 四、边界：什么时候才真的需要自定义 Agent
当然不是说自定义 Agent 完全没有价值，只有出现以下强需求时，才值得引入自定义 Agent 作为补充：

1. **深度行为模式定制**：需要彻底改变 Agent 的思维框架（比如专门做架构评审的专家代理，需要完全不同的思考逻辑和决策标准），仅靠 Skill 注入不足以修正其基础行为模式。
2. **专属工具集定制**：需要接入大量内部私有工具，且无法通过 Plugin 统一注入，必须给特定 Agent 单独配置工具集。
3. **固定协作拓扑**：需要固化多 Agent 的固定协作流程（比如固定的 需求 → 开发 → 测试 → 运维 流水线），需要自定义 Agent 作为编排节点。
4. **极强领域人设**：需要深度注入行业世界观、专业术语体系、特殊业务规则，Skill 按需加载的强度不足以支撑。

按工程实践经验，**90% 以上的企业级开发、构建、部署、运维场景，都可以通过「原生 Agent + Skill 集 + Hook 治理」的方案完全覆盖**，不需要自定义任何 Agent。

## 五、落地最佳实践
1. **Skill 优先原则**：能通过 Skill 解决的领域知识问题，绝对不写自定义 Agent。
2. **Hook 横切原则**：权限、审计、合规、校验这类通用逻辑，全部写在 Hook 里，不要散落在各个 Skill 中。
3. **最小权限原则**：给不同原生 Agent 配置差异化的 Skill 权限，比如 Explore Agent 绝不开放部署、修改类 Skill。
4. **细粒度拆分原则**：Skill 尽量拆成单一职责的小单元，方便组合复用，避免大而全的「超级 Skill」。
5. **轻量 Hook 原则**：Hook 只做拦截和管控，不写复杂业务逻辑，业务规则尽量沉淀在 Skill 中。

整体来看，OpenCode 架构的精髓——它不是一个让你写一大堆自定义 Agent 的框架，而是提供标准化的执行底座，让你通过声明式的 Skill 和可插拔的 Hook，快速搭出适配自己团队的研发工作流。
