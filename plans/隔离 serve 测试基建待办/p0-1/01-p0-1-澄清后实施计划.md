## 5. P0-1A：cleanup 确定性集成实施步骤

### 5.1 新建测试文件

### 5.2 测试文件的固定结构

测试文件必须包含以下四类内容，且都写在同一文件内，不再额外拆 helper 文件：

1. `createRepo()`  
   初始化临时 Git repo，写入一个已提交文件并生成初始 commit。
2. `git(args, cwd)`  
   仅用于该测试文件中的 Git 命令。
3. `seedEvidence(paths, worktreeDir)`  
   在 run 目录与 worktree 内制造最小 evidence。
4. 一个唯一的 integration test  
   名称固定为：`integration: real git cleanup removes only worktree and retains evidence bundle`

### 5.3 `seedEvidence()` 的固定写法

`seedEvidence()` 必须写入下列内容，弱模型不得自行增减：

1. 向 `framework-state.db` 写入一个最小 SQLite 表和 1 行数据。
2. 向 `opencode.db` 写入一个最小 SQLite 表和 1 行数据。
3. 写入：
   - `logs/serve.log`
   - `logs/sse.log`
   - `events/events.jsonl`
   - `artifacts/runtime-evidence.json`
4. 在 `worktree/.task_temp/_logs/trace.log` 写入一条框架日志，用于验证 `archiveFrameworkLogs()`。

注意：  
这里验证的是“cleanup 后证据仍可读”，不是生产 schema 正确性。  
因此 DB 内容只需最小可读表，不要伪造生产业务表。

### 5.4 集成测试的固定执行顺序

测试体只能按以下顺序写：

1. `repo = createRepo()`
2. `commit = git(["rev-parse", "HEAD"], repo).trim()`
3. `manifest = await createRunContext({ primaryWorktree: repo, commit, port: 39111, testId: "P0-1A-CLEANUP" })`
4. `await releasePortReservation(manifest.process.portReserverPid as number)`
5. `manifest.process.portReserverPid = null`
6. `setRunState(manifest, "STOPPED")`
7. `seedEvidence(manifest.paths, manifest.paths.worktreeDir)`
8. 记录 cleanup 前 `manifest.json` 与 `cleanup-report.json` 的 `mtimeMs`
9. `result = await cleanupRun(manifest.paths.rootDir)`
10. 读取并断言 cleanup 后 evidence
11. 再次重复读取 manifest/report/DB/log/artifact，断言状态不变

禁止省略第 4-6 步。  
`cleanupRun()` 只接受 `STOPPED`，如果跳过这些步骤，测试失败不代表产品缺陷。

### 5.5 必须断言的内容

必须按四组断言，不能漏项：

#### A. cleanup 成功裁决

- `result.ok === true`
- manifest 最终状态是 `CLEANED`
- cleanup report `success === true`
- cleanup report `worktreeRemoved === true`

#### B. 真实 Git worktree 已移除

- `manifest.paths.worktreeDir` 不存在
- `git worktree list --porcelain` 输出中不再包含该 worktree 路径

#### C. evidence bundle 仍然存在且可读

cleanup 后以下路径必须仍存在且可读：

- `manifest.paths.rootDir`
- `manifest.paths.manifestPath`
- `manifest.paths.cleanupReportPath`
- `manifest.paths.frameworkDbPath`
- `manifest.paths.opencodeDbPath`
- `manifest.paths.serveLogPath`
- `manifest.paths.sseLogPath`
- `manifest.paths.eventFilePath`
- `manifest.paths.artifactsDir`
- `artifacts/framework-logs/trace.log`
- `artifacts/runtime-evidence.json`

#### D. 重复读取不改状态

重复执行以下动作两次：

- `readRunManifest(rootDir)`
- 读取 `cleanup-report.json`
- 以只读方式打开两个 SQLite DB 并查询 seed 数据
- 读取 `serve.log` / `sse.log` / `events.jsonl` / `runtime-evidence.json`

并断言：

- 两次读取到的 manifest `status` 都是 `CLEANED`
- 两次读取到的 report 内容一致
- `manifest.json` 的 `mtimeMs` 不变化
- `cleanup-report.json` 的 `mtimeMs` 不变化

注意：本任务只要求“重复读取不改状态”，不要求“重复 cleanup 成功”。

## 6. P0-1B：弱模型确定性实施步骤

### 6.1 三个偏差的固定裁决

| 偏差 | 根因裁决 | 禁止 workaround | 必须实现的 gate |
|---|---|---|---|
| `database is locked` | root/child `session.created` 触发 SSE daemon 写 `session_map`，与 bootstrap 的 `createGrant/bindGrant` 竞争同一 framework DB | 固定 sleep、捕获后原地重试、直接 SQL 补 grant | 每次 session 创建后等待“对应 SSE event 已落盘 + `session_map` 行已存在”，再进入下一次 grant 写入 |
